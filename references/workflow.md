# 详细工作流（七步实战操作指南）

本文档是 SKILL.md 七步工作流的展开版，包含每步的具体工具调用、注意事项和实战复盘。开始执行攻略任务时完整读取。

---

## 第一步：需求探查与资料采集

### 操作清单

1. **识别输入类型**：用户给的是URL（帖子/视频）、上传文件（docx/pdf/图片）、还是纯文字描述？
2. **URL类输入**：
   - 用 web.fetch 抓取页面全文（包括正文、图片、评论区）。
   - 图片中的文字必须OCR提取（攻略图里常写有配方表、任务清单）。
   - 评论区可能有博主补充内容（配方、修正、延伸攻略），尝试抓取；API被风控时改用搜索核验补全。
3. **文件类输入**：用对应能力读取（docx→lark-doc/office-word，pdf→doubao-pdf，图片→Read目检+OCR）。
4. **建立原帖覆盖清单**：列出原帖已讲了哪些系统/机制，标注"原帖没说什么"——这是第三步补充的重点。

### 注意事项

- 图片是攻略的重要信息载体，不能只看文字。很多攻略帖的核心数据（配方表、肥料表、间作表）只在图片里。
- 评论区补充内容（如"饺子配方""种子对应植物大全"）是用户常点名的内容，尽量获取。
- 不要因为"看起来已经够了"就跳过图片或评论区。

### 实战复盘（饥荒攻略）

- 原帖8章正文+12道菜谱图+肥料表+间作表+夏季任务清单，第一次抓取时部分图片下载失败，重新抓取才获得完整OCR数据。
- 评论区API两次被风控（-352/-404），改为多源搜索核验补全（波兰水饺配方、14种作物喂鸟换种子机制）。

---

## 第二步：创建飞书文档容器

### 操作清单

1. 读取 lark-doc skill 的 online-doc 模块和 create 参考。
2. 用 docs +create 创建最小容器：
   - `<title>`：面向用户需求的标题（如"饥荒联机版新手教程（扩充详解版）"）
   - 一个简短 callout：说明文档正在生成
3. 记录 document_id 和 URL，后续所有写入都用这个 ID。

### 注意事项

- 不要先写几万字正文再建文档——建容器是第一步，正文后续逐步写入。
- 不要创建第二个文档（如"先建一个草稿再合并"），所有内容写进同一个文档。

---

## 第三步：全网多源检索补充

### 操作清单

1. **明确补充范围**：基于第一步的"原帖没说什么"清单，列出需要补充的系统。
2. **多源并行搜索**：用 general_search 对每个系统做2~3个不同关键词的搜索（中文+英文）。
3. **用户点名优先**：用户明确提到的系统（如"月圆事件""雕像""玩偶服""洞穴""海上漩涡""新地图"）必须覆盖，再扩展到其他系统。
4. **记录来源**：每条关键事实记录来源URL，交付时可追溯。

### 搜索关键词技巧

- 机制类："XX 机制 详解"、"XX 怎么触发"、"XX 条件"
- 道具类："XX 配方"、"XX 掉落"、"XX 有什么用"
- 地点类："XX 位置"、"XX 怎么去"、"XX 地形"
- 版本核验："XX 联机版"、"XX 单机版 区别"、"XX 最新版本"

### 注意事项

- 搜索结果可能互相矛盾，不要取第一个就用，至少2~3个来源交叉确认。
- 注意区分"攻略经验"和"事实数据"——经验类（"我觉得XX好用"）可参考，数据类（"XX掉率50%"）必须核验。
- 英文维基（Fandom）通常数据最准确，中文攻略站经验更丰富，两者结合。

---

## 第四步：大规模分片并行研究

### 何时触发

当攻略需要覆盖的独立系统 ≥ 4个，或预计正文超过2万字时，创建 OrganizerAgent 分片并行。

### 分片原则

- 按游戏系统自然划分（如：月圆/雕像/时装、洞穴、海洋、地形/角色/科技、生物/天气/机制、烹饪/保鲜/装备）。
- 每个分片是独立的端到端 pipeline：检索→核验→写XML→自检。
- 分片数量2~4个为宜，平衡并行度和合并成本。

### 给组织者的任务书必须包含

1. 文档ID和URL
2. 分片清单和每片覆盖范围
3. 输出格式：飞书XML片段（h1/h2/h3+callout+table+grid），每章开头"本章怎么用"
4. 事实核验要求：多来源交叉，不确定标"以游戏内为准"
5. 重点：补充原帖未覆盖内容，原帖已覆盖的只深化不重复
6. 用户点名系统优先

### 合并注意事项

- 各分片可能对同一事实给出矛盾数据（如月相周期、切斯特形态），合并时必须统一核验。
- 章节编号在合并时重新编排，不要让各分片自己编号。
- 合并后生成总览章节（目录速查表+核验说明）。

## 第五步：事实核验与冲突处理

### 常见冲突类型

| 冲突类型 | 示例 | 处理方式 |
|---|---|---|
| 单机vs联机 | 月相周期16天(单机) vs 20天(联机) | 以联机版为准，在文档中注明修正 |
| 本体vs DLC | 海洋有鲨鱼(船难DLC) vs 无鲨鱼(联机本体) | 明确标注版本，剔除DLC内容 |
| 旧版本vs当前 | 配方材料数量随版本变化 | 标注"以游戏内为准"，不写死 |
| 以讹传讹 | "冰雪切斯特联机版不存在" | 多源核验后修正，写明结论 |
| 命名混淆 | "双子魔眼"(泰拉瑞亚) vs "恐怖之眼"(DST联动) | 用游戏内官方名称 |

### 核验方法

1. 优先查官方Wiki/Fandom的当前版本数据。
2. 多个中文攻略站交叉确认。
3. 视频攻略（B站/抖音）的实机画面是有力证据。
4. 仍无法确认的，标注"以游戏内为准"，不编造。

### 核验结论写入文档

把重要的修正结论用callout高亮写入文档（如"DST月相为20天周期，'16天'是单机版规则"），这是攻略价值的重要体现。

## 第六步：结构化写作与真实配图

### 写作规范

详见 [xml-patterns.md](xml-patterns.md)。核心要求：
- 每章开头"本章怎么用"callout
- 数据表格化
- 风险/易错点callout高亮
- XML标签配平

### 配图流程

1. **搜索**：image_search 搜索章节主题关键词（如"饥荒联机版 月岛"、"饥荒 远古区 遗迹"）。
2. **下载**：curl -L 下载候选图到本地。
3. **目检**：Read 查看图片，确认：
   - 是真实游戏截图（不是立绘、不是宣传图、不是AI生成）
   - 画面主体对应章节主题
   - 无大面积营销水印/宣传卡片
   - 分辨率：**纯游戏画面不设最低门槛**，画面主体清晰可辨即可（低分辨率也保留）；**含文字/表格/数据的图片必须 ≥1920×1080 且文字放大后清晰可读**
   - 版本正确（不是单机版/DLC画面）
   - **含密集文字/表格的图片如果模糊到不可读，直接弃用；对应数据改用文档内 table 呈现，图片只保留纯场景展示**
4. **上传插入**：lark-cli docs +media-insert 或 block_insert_after 用 `<img path="@./xxx.jpg"/>` 插入到章节h1之后。
5. **caption**：每张图带简短说明文字。

### 含密集文字图片的处理决策流程（强制）

当某张图片包含密集文字/表格/数据（如食谱表、配方图、科技栏、制作栏、地图、属性面板）时，必须按以下顺序决策：

```
图片含密集文字/表格/数据？
├─ 否（纯游戏画面：场景、战斗、Boss、地形、角色、建家布局等）
│   └─ 不设最低分辨率门槛，画面主体清晰可辨即可 → 保留（低分辨率也保留，
│      因为游戏画面的价值在于视觉展示，强行用文字代替会失去图文并茂的意义）
└─ 是（食谱表、配方图、科技栏、制作栏、地图、属性面板等）
    ├─ 文字放大后清晰可读（≥1920×1080 或等效清晰度）？
    │   ├─ 是 → 保留
    │   └─ 否（模糊/低分辨率）
    │       ├─ 能否搜到更清晰的同主题实机截图？
    │       │   ├─ 能 → 下载目检后替换原图
    │       │   └─ 不能 → 进入下一步
    │       └─ 文档内是否已有对应数据的文字/表格？
    │           ├─ 有 → 直接删除该模糊图片，文字表格已足够
    │           └─ 没有 → 在文档中新建 table 呈现数据，然后删除模糊图片
    └─ 最终原则：模糊的数据图宁可不用，也不放一张看不清的图；
                但纯游戏画面永远不因分辨率低而删除
```

**典型案例（饥荒攻略实战）**：
- 常用食谱速查表（620×690，文字密集模糊）→ 第七章已有完整菜谱表格 → 直接删除
- 科学机器科技栏（550×407，UI文字密集模糊）→ 搜不到清晰纯实机版 → 第二十八章已有文字描述 → 删除
- 烹饪锅食谱界面（896×585，UI文字密集）→ 搜到1192×671清晰版 → 替换
- 制作栏界面（550×407，分类标签文字密集）→ 搜到1401×707清晰版 → 替换
- 洞穴入口陷坑（462×243，**纯游戏画面**，虽低分辨率）→ **保留**，画面展示了洞穴入口的样子，有视觉价值
- test.jpg ×2（与其他图片完全重复）→ 重复内容，删除（与分辨率无关）

### 配图数量

- 每章1~2张，不要堆图。
- 已有图的章节不重复插入。
- 总览/目录章不需要图。
- 纯数值章节找不到实体画面时，用游戏内界面截图或跳过，不硬凑。

## 第七步：验证与迭代交付

### 验证清单

详见 [quality-check.md](quality-check.md)。核心验证：
1. docs +fetch --scope outline 确认章节数和标题正确。
2. keyword搜索确认关键内容存在（如用户点名的系统）。
3. 抽查章节确认图片在h1之后、caption正确。
4. 确认无XML代码泄漏、无占位符残留。
5. 确认无用户要求删除的内容残留（如出处文案、AI生成声明）。

### 交付

- present_files 交付飞书文档链接。
- 回复中说明：完成了什么、覆盖了哪些系统、关键核验结论、仍标注"以游戏内为准"的项。
- 不要粘贴完整正文，不要解释内部执行过程。

### 迭代

- 用户指出理解偏差时，立即修正，不辩解。
- 用户要求补充某章细节时，优先唤醒已有组织者（如还存活）复用上下文，不必新建。
- 每次编辑后必须重新 fetch 验证并重新 present_files 交付。
